## 1. System Philosophy

The platform solves a core trust problem: how do you safely return a lost item and reward the finder without either party getting scammed?

**Three golden rules:**

- **Escrow First:** The reward money enters the system before the handoff happens. No money, no meeting.
- **OTP Handshake:** A 4-digit code is generated by the system, shown only to the Owner after payment, and spoken aloud during the physical meetup. The Finder types it in to release their payout. This proves the item was physically handed over.
- **Privacy by Default:** The public feed never shows serial numbers, exact locations, or contact info. These are only revealed after admin approval and payment.

## 2. User Roles

There are **three roles**. All users share the same login/registration. Role is determined by a `role` field in the User document.

| Role | How They Get It | What They Can Do |
|------|----------------|-----------------|
| `user` | Default on registration | Post lost/found items, claim items, pay rewards, receive payouts |
| `admin` | Manually promoted by another admin | Everything a user can do, PLUS access the Admin Panel tab |

> **Note:** There is no separate admin login page. An admin is just a user with elevated privileges. The Admin Panel tab is conditionally rendered in the dashboard if `user.role === 'admin'`.

## 3. Database Schema

### 3.1 Users Collection

```
{
  _id,
  name,
  email,
  passwordHash,
  phone,           // M-Pesa registered number (e.g. 2547XXXXXXXX)
  role,            // "user" | "admin"
  createdAt
}
```

### 3.2 Items Collection

Each item (lost or found) is one document.

```
{
  _id,
  type,            // "lost" | "found"
  postedBy,        // User _id (the Finder if type=found, the Owner if type=lost)
  
  // Public fields (shown on Global Feed)
  title,           // Generic: "Black Laptop Bag" NOT "My Dell XPS"
  category,        // "Electronics" | "ID/Cards" | "Clothing" | "Books" | "Other"
  locationGeneral, // "Main Library" | "Science Block" | "Cafeteria" etc.
  dateReported,
  photo,           // Generic photo URL
  rewardAmount,    // Only relevant for "lost" items (set by Owner)

  // Private fields (hidden from public, shown to Admin only during review)
  locationExact,   // "2nd floor, desk near the window"
  privateDescription, // Serial number, scratches, unique marks, what was inside
  privatePhoto,    // Close-up showing identifying marks

  status,          // See Status Reference below
  matchedItemId,   // _id of the paired lost/found item (set when a claim is approved)

  createdAt,
  updatedAt
}
```

### 3.3 Claims Collection

Created when an Owner clicks "Claim This Item" on a Found item.

```
{
  _id,
  foundItemId,     // _id of the Found item being claimed
  lostItemId,      // _id of the Owner's Lost post (optional but helpful for matching)
  claimedBy,       // Owner's User _id
  
  // Owner's proof of ownership answers
  proofAnswers: {
    question1: "...",
    question2: "...",
    question3: "..."
  },

  adminVerdict,    // null | "approved" | "rejected"
  adminNote,       // Optional note from admin explaining decision
  reviewedBy,      // Admin User _id
  reviewedAt,

  createdAt
}
```

### 3.4 Transactions Collection

Created when Admin approves a claim (in anticipation of payment).

```
{
  _id,
  claimId,         // _id of the approved Claim
  foundItemId,     // _id of the item
  ownerId,         // User _id of the person paying
  finderId,        // User _id of the person to be paid
  
  totalAmount,     // Full reward amount
  finderCut,       // 80% of totalAmount
  platformCut,     // 20% of totalAmount

  // STK Push (Owner pays in)
  stkCheckoutRequestId,  // From Daraja STK Push response
  stkStatus,             // "pending" | "success" | "failed"
  
  // OTP Handshake
  otpCode,         // 4-digit code (generated by backend on payment success)
  otpVerified,     // false | true

  // B2C Payout (Finder receives)
  b2cConversationId,     // From Daraja B2C response
  b2cStatus,             // "pending" | "success" | "failed"

  status,          // "awaiting_payment" | "escrowed" | "released" | "refunded" | "disputed"
  createdAt,
  updatedAt
}
```

## 4. Page & UI Architecture

### 4.1 Landing Page (Unauthenticated)

What a visitor sees before logging in.

- Hero with a campus-focused tagline explaining the concept
- Two big CTA buttons: **"I Lost Something"** and **"I Found Something"** — both redirect to login/register
- Live counters: Items Reunited | Active Escrows | Rewards Paid
- Navigation: Logo | Global Feed link | Login | Register

### 4.2 Global Feed (Public, Read-only for guests)

Visible to everyone. Two tabs: **Lost Items** and **Found Items**.

**Each item card shows:**
- Generic photo
- Generic title and category
- General location
- Date reported
- Reward amount (on Lost items only)
- A **"Claim This Item"** button (requires login — only on Found items)

**What is deliberately hidden:**
- Serial numbers / IMEI
- Exact location (desk, floor, room number)
- Contact details
- Unique identifying marks

**Search & Filter bar:** Filter by category, general location, and date range.

### 4.3 Private Dashboard (Authenticated Users)

The user's personal control center. Three tabs:

#### Tab 1 — My Lost Reports
- Lists all lost items the user has posted
- Shows current status (Searching / Claimed / Resolved)
- After payment: shows **Finder's phone number** + **4-digit Handshake Code** in large bold text
- "Report a Lost Item" button at the top

#### Tab 2 — My Found Reports
- Lists all found items the user has reported
- Shows current status (Unclaimed / Pending Review / Awaiting Payment / Ready for Handoff / Resolved)
- When status is **Ready for Handoff**: shows the Owner's phone number + an input box labeled **"Enter Handshake Code"** + a **"Verify & Release Funds"** button
- "Report a Found Item" button at the top

#### Tab 3 — My Active Claims
- Lists all claims the user has submitted (items they're trying to claim from the Found Feed)
- Shows the claim status (Pending Admin Review / Approved / Rejected / Awaiting Payment / Ready for Handoff / Resolved)
- When status is **Awaiting Payment**: shows a **"Pay Reward"** button
- When status is **Ready for Handoff**: shows Finder's phone number + Handshake Code

### 4.4 Admin Panel Tab (Admins Only)

Only visible if the logged-in user has `role === 'admin'`. Appears as an extra tab inside the dashboard.

Three queues:

#### Queue 1 — Pending Claims
- Side-by-side view: Finder's private details vs. Owner's proof answers
- **Approve** and **Reject** buttons
- Optional text field for admin notes

#### Queue 2 — Escrow Ledger
- Table of all transactions with statuses
- Manual override buttons: "Trigger Refund" | "Mark as Disputed"

#### Queue 3 — User Management
- List of all users
- **Promote to Admin** and **Ban User** buttons

## 5. Full Item Lifecycle & Workflow

### Phase 0 — Reporting (Populating the Feeds)

**Scenario A: Owner posts first**
1. Owner fills out the "Report Lost Item" form
   - Public fields (title, category, general location, photo, reward amount)
   - Private fields (exact location, serial number, unique marks, private photo)
2. Item is saved with `status: "searching"` and `type: "lost"`
3. It appears on the **Global Lost Feed**
4. If a similar Found item already exists, the system flags a **Suggested Match** on the Owner's dashboard

**Scenario B: Finder posts first**
1. Finder fills out the "Report Found Item" form
   - Public fields only (generic title, category, general location, generic photo)
   - Private fields (exact location where found, any identifying details noticed)
2. Item is saved with `status: "unclaimed"` and `type: "found"`
3. It appears on the **Global Found Feed**

> Both scenarios can co-exist. The system handles both orders gracefully.

---

### Phase 1 — The Claim

1. Owner scrolls the **Global Found Feed** (or checks their Suggested Matches tab)
2. Owner identifies their item and clicks **"Claim This Item"**
3. A modal opens with dynamic proof-of-ownership questions based on category:
   - **Electronics:** "What is the lock screen wallpaper?", "What is the serial number?", "Any physical damage?"
   - **ID/Cards:** "What is the full name on the ID?", "What is the institution?"
   - **Clothing:** "What is the brand?", "Any labels or markings inside?"
   - **Books:** "What is written on the inside cover?", "Any page highlights or notes?"
4. Owner submits answers. A `Claim` document is created in the database
5. The Found item's status changes from `unclaimed` → `pending_review`
6. The item **disappears from the Global Found Feed** so no one else can claim it simultaneously
7. The claim appears in the Owner's **My Active Claims** tab with status **"Pending Admin Review"**

---

### Phase 2 — Admin Review

1. Admin sees the new claim in **Queue 1** of the Admin Panel
2. Admin views a side-by-side comparison:
   - Left: Finder's private description and photos
   - Right: Owner's submitted proof answers
3. Admin makes a decision:

**If Rejected:**
- The Claim document is marked `adminVerdict: "rejected"`
- The Found item returns to `status: "unclaimed"` and reappears on the Global Found Feed
- Owner is notified: "Your claim was rejected. Reason: [admin note]"

**If Approved:**
- The Claim document is marked `adminVerdict: "approved"`
- The Found item status changes to `awaiting_payment`
- A `Transaction` document is created with `status: "awaiting_payment"`
- Owner sees **"Claim Approved — Pay Reward"** in their My Active Claims tab

---

### Phase 3 — Escrow Payment (STK Push)

1. Owner clicks **"Pay Reward"** in their My Active Claims tab
2. A simple modal appears: **"Enter your M-Pesa number"** (pre-filled if they have a phone on file)
3. Backend receives the number and triggers **Daraja STK Push**:
   - A payment prompt appears on the Owner's phone
   - Owner enters their M-Pesa PIN
   - Money goes to the system's Paybill/Till number
4. Daraja sends a **callback** to the backend confirming payment success
5. On callback success:
   - Transaction status updates to `escrowed`
   - Found item status updates to `ready_for_handoff`
   - Backend generates a **random 4-digit OTP code** and saves it to the Transaction document
   - **Both users' dashboards update:**
     - **Owner (My Active Claims):** Finder's phone number is revealed + OTP code shown in large bold text. A note reads: *"Give this code to the Finder ONLY after you have inspected and received your item."*
     - **Finder (My Found Reports):** Owner's phone number is revealed + an input box appears with label: *"Enter Handshake Code"*

---

### Phase 4 — Physical Handoff

1. Owner calls the Finder using the revealed phone number
2. They agree on a meetup location (e.g., campus library)
3. They meet. The Owner inspects the item.
4. If satisfied, the Owner verbally tells the Finder: **"The code is 4921"**
5. The Finder types `4921` into the input box on their **My Found Reports** tab and clicks **"Verify & Release Funds"**

---

### Phase 5 — Payout (B2C)

1. Backend receives the OTP submission
2. Backend verifies: does the submitted code match `transaction.otpCode`?

**If code is wrong:**
- Error message shown: "Incorrect code. Please ask the owner to confirm."
- Nothing changes. The Owner still has the correct code.

**If code is correct:**
- `transaction.otpVerified` is set to `true`
- Transaction status updates to `released`
- Found item status updates to `resolved`
- Lost item (if linked) status updates to `resolved`
- Backend triggers **Daraja B2C API** to send 80% of funds to the Finder's registered M-Pesa number
- 20% remains in the system Paybill
- Both dashboards show a **"Resolved ✓"** badge on the item

## 6. Item Status Reference

### Found Items

| Status | Meaning | Visible on Global Feed? |
|--------|---------|------------------------|
| `unclaimed` | Posted, waiting for an owner to claim | Yes |
| `pending_review` | An owner has submitted a claim; admin reviewing | No |
| `awaiting_payment` | Claim approved; waiting for owner to pay | No |
| `ready_for_handoff` | Payment received; phones revealed, OTP active | No |
| `resolved` | OTP verified; payout sent; item returned | No |
| `disputed` | Something went wrong; admin intervention needed | No |

### Lost Items

| Status | Meaning |
|--------|---------|
| `searching` | Posted, no match yet |
| `claim_pending` | Linked claim is under admin review |
| `claim_approved` | Admin approved; awaiting payment |
| `awaiting_handoff` | Payment made; handoff in progress |
| `resolved` | Item returned successfully |

## 7. M-Pesa Daraja Integration

> Implement this last after all other features are working with mock data.

### 7.1 STK Push (Owner → System)

Used in **Phase 3** to collect the reward from the Owner.

**Endpoint to build:** `POST /api/payments/stk-push`

**Flow:**
```
1. Backend sends STK Push request to Daraja API
   - Amount: rewardAmount from the Lost/Found item
   - PhoneNumber: Owner's M-Pesa number
   - AccountReference: "LostFound-[itemId]"
   - TransactionDesc: "Reward Escrow for [item title]"

2. Daraja returns a CheckoutRequestID → save to Transaction document

3. Owner's phone vibrates with M-Pesa prompt → enters PIN

4. Daraja calls your callback URL: POST /api/payments/stk-callback
   - Check ResultCode === 0 (success)
   - Update transaction.stkStatus = "success"
   - Generate OTP and update item status
```

**Sandbox test credentials:** Use Daraja sandbox (test.safaricom.co.ke). No real money moves.

### 7.2 B2C (System → Finder)

Used in **Phase 5** to pay the Finder after OTP verification.

**Endpoint to build:** `POST /api/payments/b2c-payout`

**Flow:**
```
1. Backend sends B2C request to Daraja API
   - Amount: transaction.finderCut (80%)
   - PartyB: Finder's phone number
   - Remarks: "Lost & Found Reward - [item title]"

2. Daraja returns ConversationID → save to Transaction document

3. Daraja calls your result callback URL: POST /api/payments/b2c-callback
   - Confirm success
   - Update transaction.b2cStatus = "success"
   - Final item status = "resolved"
```

| Phase | What to Do |

## 8. Admin Panel Workflows

### 8.1 Approving/Rejecting a Claim

```
Admin opens Queue 1 → Pending Claims
→ Clicks on a claim card
→ Side-by-side view opens
   Left side: Finder's private description + private photos (from Item.privateDescription, Item.privatePhoto)
   Right side: Owner's proof answers (from Claim.proofAnswers)
→ Admin clicks "Approve" or "Reject" with optional note
→ System updates claim.adminVerdict and item.status accordingly
```

### 8.2 Handling a Dispute

Triggered when an owner pays but the meetup never happens (48+ hours pass with no OTP entry):

```
Owner clicks "Something went wrong" / "Raise Dispute" button
→ Item status changes to "disputed"
→ Admin sees it in Queue 2 (Escrow Ledger) highlighted in red
→ Admin can:
   - Trigger B2C refund to Owner (if Finder is at fault)
   - Release payment to Finder (if Owner is at fault)
```

### 8.3 Auto-Archive 
- If a claim stays `awaiting_payment` for 48 hours after approval → auto-expire; item returns to `unclaimed`

## 9. Edge Cases & Dispute Handling

| Scenario | System Response |
|----------|----------------|
| Owner tries to claim their own found post | Block: check if `foundItem.postedBy === currentUser._id` |
| Two owners claim the same item simultaneously | Only the first claim locks the item to `pending_review`; second gets "Item already under review" |
| Owner enters wrong OTP on purpose | Finder cannot verify; item stays in `ready_for_handoff`; no funds released |
| Finder gives wrong item intentionally | Owner does not give the OTP code; Finder cannot release funds; Owner raises a dispute |
| M-Pesa payment deducted but callback fails | Admin can manually confirm from Escrow Ledger using the CheckoutRequestID from Daraja |
| Finder's phone number changes | Admin can update it from User Management |
